# Seguimiento 3 — Pruebas de funcionamiento y fallos de SQLite

## Alcance y procedencia de la evidencia

El proyecto corresponde al **perfil A, con SQLite como único motor**, según `README.md` y `docs/decisiones.md`. El fallo de un motor secundario **no aplica**: no se documenta una prueba de conmutación ni un motor alternativo. La cobertura descrita a continuación corresponde exclusivamente a pruebas existentes en el código.

El **30/10/2026** se ejecutó el siguiente comando, con **11 pruebas aprobadas en 6.367 segundos**:

```powershell
py -m unittest tests.test_sqlite_failure_v16 tests.test_error_handling tests.test_connection -v
```

Este resultado fue aportado para este registro; no se volvió a ejecutar el comando al redactar el documento. La distribución comprobable en el código es una prueba de `test_sqlite_failure_v16`, ocho de `test_error_handling` y dos de `test_connection`. No se dispone aquí de un archivo separado con la salida completa de esa ejecución: este documento registra el resultado suministrado y los archivos de pruebas permiten revisar sus aserciones.

**Observación no bloqueante:** se reportó una advertencia `ResourceWarning`. Se consigna separadamente del resultado satisfactorio de las 11 pruebas; no se atribuye a un recurso o caso concreto ni se afirma que haya sido corregida, porque no se aportó su detalle.

Las pruebas de `tests/test_http_crud_s2.py` **no forman parte de esas 11 pruebas**. Su evidencia anterior es [evidencia_s2_windows.md](../../evidencia_s2_windows.md), fechada el 23/10/2026: 33/33 pruebas aprobadas en 5.698 segundos, con cobertura HTTP de login, CRUD, alertas, errores 400 y escrituras sin sesión. Es evidencia automatizada con HTTP y SQLite temporales en localhost; no acredita una nueva ejecución S3 ni una demostración manual en CRNube.

## Respuestas verificadas y comportamiento ante fallos

- **HTTP 400:** formato inválido de `editar` en cuentas y cotización `NaN` en transferencias, en las pruebas S3 indicadas; monto negativo al crear un movimiento, en la evidencia anterior S2.
- **HTTP 409:** categoría duplicada, borrado de categoría referenciada por un presupuesto y transferencia abortada por el trigger de prueba. No se generaliza el estado a cualquier excepción SQLite.
- **HTTP 503:** fallo de conexión SQLite simulado en GET `/health`, fallos durante autenticación GET/POST, bloqueo real de escritura y error de permisos de almacenamiento simulado en el dashboard.
- **HTTP 500:** `RuntimeError` simulado en `dashboard_page` durante GET `/`. No se presenta como resultado de cualquier fallo de base de datos.

Al fallar SQLite en estos escenarios, la aplicación responde con errores controlados y mensajes que las pruebas revisan para evitar detalles internos. El bloqueo de escritura no deja la categoría fallida y permite repetir después de liberarlo; el fallo transaccional revierte la categoría temporal y cierra la conexión; el fallo de transferencia revierte también la cotización. La consulta costosa se interrumpe con `SQLITE_INTERRUPT` y la conexión siguiente funciona. La inicialización CLI fallida termina con código 1 y mensaje controlado. Ninguno de estos casos demuestra conmutación a un motor secundario, recuperación automática ante cualquier fallo ni disponibilidad permanente.

La duración agregada de 6.367 segundos corresponde a la suite comunicada, no a una medición de rendimiento de SQLite. Este documento no añade pruebas, ejecuciones ni mediciones a las evidencias descritas.
